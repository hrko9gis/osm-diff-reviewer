# 企画書:OSM 参照データ照合レビュー QGIS プラグイン(仮称 OSM Diff Reviewer)

作成日:2026-10-03
位置づけ:Claude Code での開発に先立つ企画・要件文書。実装前に「12. 未決事項」を確定させる。

## 1. 概要

外部の参照データ(自治体オープンデータ、基盤地図情報など)と OpenStreetMap を QGIS 上で照合し、差分を更新候補として一覧化・レビューするプラグイン。OSM への編集は行わず、候補を JOSM(個人作業)と MapRoulette(共同作業)へ引き渡す。

一文で言えば「統合の前段(照合とレビュー)を QGIS で担い、編集は既存エディタに任せる」。

## 2. 背景

2026-10 時点の調査結果。

- JOSM Conflation プラグインは統合まで行えるが、参照データを OSM ファイルとして JOSM に読み込む必要がある。
- Osmose にも外部データとの突き合わせ機能があるが、解析器の追加はサーバ側の作業で、手元のデータを気軽に試す用途には向かない。
- 既存の照合ツールは建物・POI など特定地物向けが多く、実務では各自が Python スクリプトや QGIS で都度比較している。
- 照合結果を一覧で確認・共有でき、統合後に再実行しても全件を見直さずに済む仕組みは、OSM コミュニティで要望として挙がっている。
- QGIS 公式リポジトリの OSM 関連プラグインに、汎用の照合レビュー機能を持つものは見当たらなかった。
- JOSM 起動は QuickOSM、Mapillary 表示は MapillaryClickPreview が既に提供しているため、これらは再実装しない。
- MapRoulette のチャレンジ作成は、QGIS で GeoJSON に変換して Web 画面から手動登録するのが現状の流れ。QGIS プラグインは見当たらなかった。

## 3. 対象ユーザーと利用シナリオ

| ユーザー | シナリオ |
|---|---|
| 個人マッパー | 自治体が公開した施設一覧と OSM を照合し、未登録・名称違いを JOSM で1件ずつ直す |
| 地域コミュニティの世話役 | 照合結果を MapRoulette のチャレンジにして参加者に分担させ、進捗を QGIS で把握する |
| 参照データの更新を追う人 | 参照データの旧版と新版の差分から現実の変化を抜き出し、OSM に未反映の箇所だけを確認する |

## 4. スコープ

やること

- 参照レイヤと OSM データの照合、差分の分類、スコア付け
- レビュー状態の記録と、再実行時の引き継ぎ
- 参照データの版間差分モード
- 参照データのライセンス・出典の記録と、書き出し時のゲート
- JOSM への引き渡し(リモートコントロール)
- MapRoulette への引き渡し(GeoJSON 書き出し、API によるチャレンジ作成、進捗同期)

やらないこと

- OSM API への直接アップロード、`.osc` の生成
- 自動統合(ジオメトリやタグの自動マージ)
- 街路画像ビューア、OSM データの汎用ダウンロード UI(既存プラグインに任せる)
- リレーションの照合(初期版では対象外)

## 5. 機能要件

### 5.1 入力

- 参照レイヤ:QGIS に読み込まれた任意のベクタレイヤ。座標系は内部で変換する。距離計算は投影座標系で行う(既定は対象範囲に応じた平面直角座標系または UTM。プロジェクト CRS が投影系ならそれを使う)。
- 参照レイヤの安定キー:ユーザーが ID フィールドを指定する。無い場合はジオメトリと主要属性のハッシュで代用する(その場合、参照データの形状が変わると別地物扱いになる旨を UI に表示)。
- OSM データ:(a) Overpass API から対象範囲とタグ条件で取得、(b) ローカルの `.osm` / `.osm.pbf`、(c) 既に QGIS にある OSM 由来レイヤ、の3通り。いずれも OSM の種別・ID・version・timestamp を保持する。(c) でこれらが欠ける場合は JOSM 引き渡しを無効化する。
- 属性対応表:参照フィールドから OSM タグへの対応(例:`名称` → `name`)と比較方法(完全一致、正規化後一致、類似度)を定義し、JSON プロファイルとして保存・再利用する。

### 5.2 照合と分類

| 分類 | 条件 |
|---|---|
| 一致 | 対応する OSM 地物があり、形状・属性とも閾値内 |
| 未登録 | 探索半径内に対応候補がない参照地物 |
| 形状差 | 対応はあるが形状指標が閾値を外れる |
| 属性差 | 対応はあるが対応表上の属性が食い違う |
| 曖昧 | 候補が複数あり一意に決まらない(多対多を含む) |
| OSM のみ | 参照側に対応がない OSM 地物。参照データが網羅的な場合のみ意味を持つので既定はオフ |

各ペアに距離、形状類似度、属性一致度、総合スコアを持たせる。閾値と探索半径は地物種別ごとに設定可能とし、プロファイルに含める。

### 5.3 レビュー

- ドックウィジェットに候補一覧を表示。分類・スコア・状態で絞り込みと並べ替えができる。行を選ぶと地図が該当箇所へ移動し、参照地物と OSM 地物を強調表示、属性を左右に並べて示す。
- 状態:未確認 / 要編集 / 反映済み / 対応不要(参照側の誤り) / 対応不要(OSM が正しい) / 保留。メモ欄を持つ。
- 状態は GeoPackage に保存する。再実行時は「参照キー + OSM 種別・ID」で前回の判定を引き継ぎ、対応不要とした差分は既定で非表示にする。
- 引き継ぎの例外:前回から参照側の属性・形状、または OSM 側の version が変わったペアは「要再確認」の印を付けて再表示する。

### 5.4 版間差分モード

参照データの旧版と新版を安定キーで突き合わせ、追加・削除・変更を抽出する。その結果だけを OSM と照合する。

- 追加:OSM に既に存在するか
- 削除:OSM にまだ残っているか
- 変更:OSM が旧版と新版のどちらに近いか

### 5.5 ライセンスゲート

参照レイヤごとに、ライセンス名、出典表記、OSM での利用可否の確認状況(確認済み / 未確認 / 不可)、根拠 URL を記録する。「確認済み」でないレイヤについては、参照データの属性や形状を外部に出す操作(5.6 の参照形状送信、5.7 の書き出しと API 送信)を止める。照合とレビューそのものは止めない。

### 5.6 出力 A:JOSM への引き渡し

- JOSM リモートコントロール(既定 `http://127.0.0.1:8111`)を使う。接続確認を行い、未起動なら案内を出す。
- 既存地物に関する候補(形状差・属性差・OSM のみ):周辺範囲を読み込み、該当オブジェクトを選択した状態で開く。
- 未登録の候補:周辺範囲を読み込む。任意で、参照地物を提案タグ付きの別レイヤとして JOSM に渡す(ライセンスゲート通過時のみ。アップロード対象のレイヤには入れない)。
- 一覧から「次の候補を開く」で連続処理できる。
- JOSM から戻ったあと、ユーザーが状態を更新する。任意の「反映確認」で該当 OSM 地物の version を再取得し、変化を検出する。

### 5.7 出力 B:MapRoulette 連携

段階的に実装する。

1. GeoJSON 書き出し:1候補を1タスクとし、分類、参照側の属性、対応する OSM 地物の ID をプロパティに含める。タスク説明文のテンプレートを設定できる。
2. API によるチャレンジ作成:プロジェクトを選び、名称・説明・手順・変更セットコメントを入力して作成する。API キーは QGIS の認証データベース(QgsAuthManager)に保存し、設定ファイルやプロジェクトファイルに書かない。
3. 進捗同期:タスク状態を取得し、レビュー状態に反映する(修正済み → 反映済み、問題なし → 対応不要、スキップ・難しい → 保留)。同期は手動実行とする。

MapRoulette への掲載は参照データの再配布にあたり得るため、ライセンスゲートの対象とする。

## 6. 非機能要件

- 対応バージョン:QGIS 3.40 LTR 以上および QGIS 4 系(案。12 で確定)。Qt のインポートは `qgis.PyQt` 経由に統一し、Qt5 / Qt6 の両方で動くようにする。
- 依存:QGIS 同梱の Python ライブラリのみ。追加の pip 依存を持たない。
- 通信:`QgsNetworkAccessManager` / `QgsBlockingNetworkRequest` を使い、QGIS のプロキシ設定に従う。Overpass のエンドポイントは設定可能にする。User-Agent は QGIS が自身の値(`Mozilla/5.0 QGIS/…`)で上書きするため、プラグインの識別は Referer ヘッダ(リポジトリ URL)で示す(M3 で確認)。例外として、JOSM リモート制御(このコンピュータ上)への通信は QGIS のプロキシ設定を通さず直接送る。QGIS 3 系では 127.0.0.1 宛てでもプロキシ経由になり、接続に失敗するうえ参照データが外部に出るため(M3 で確認)。JOSM・Overpass への通信はバックグラウンドで行い、QGIS の画面を止めない。
- 性能:参照・OSM とも数万地物で、照合が数分以内に終わること。`QgsSpatialIndex` で候補を絞り、処理は `QgsTask` またはプロセッシングでバックグラウンド実行する。
- 多言語:日本語と英語。文字列は `tr()` で包む。
- ライセンス:GPL v2 以降(QGIS プラグインの要件)。
- 安全:OSM への書き込み経路を持たない。外部送信は JOSM(ローカル)、Overpass、MapRoulette の3つに限る。

## 7. データ設計

作業用 GeoPackage 1ファイルに以下を持つ。プロジェクトごとに1ファイル。

| テーブル | 主な内容 |
|---|---|
| `reference_sources` | 参照レイヤの識別子、ライセンス、出典、確認状況、根拠 URL、キーフィールド |
| `runs` | 実行日時、プロファイル(閾値・属性対応表)の JSON、対象範囲、OSM 取得時刻 |
| `candidates` | 実行 ID、参照キー、OSM 種別・ID・version、分類、各スコア、代表ジオメトリ |
| `reviews` | 参照キー、OSM 種別・ID、状態、メモ、判定時の参照ハッシュと OSM version、更新日時 |
| `mr_tasks` | 候補とチャレンジ ID・タスク ID の対応、最終同期時の状態 |

`reviews` は実行をまたいで保持する。`candidates` は実行ごとに追加する。

## 8. 照合アルゴリズムの方針

- ポイント対ポイント:距離と名称類似度。名称は正規化(全角半角、空白、法人格表記など)してから比較する。
- ポイント対ポリゴン:参照がポイント、OSM が建物や敷地のポリゴンである場合を扱う。包含または近接で対応付ける。
- ポリゴン対ポリゴン:重なり率(IoU)と重心距離。
- ライン対ライン:バッファ重なり率とハウスドルフ距離。分割単位の違い(参照1本に OSM 複数本)があるため、初期版は「曖昧」に多く落ちる前提で、精度向上は後続フェーズとする。
- 対応付け:スコア順の貪欲法で一対一を決め、僅差の競合は「曖昧」とする。
- 照合処理はプロセッシングアルゴリズムとして公開し、GUI なしで実行・テストできるようにする。

## 11. テスト方針

- `core/` は単体テストを中心にする。小さな試験データ(参照・OSM の対で、期待する分類を持つもの)をリポジトリに含める。試験データは自作するか、ライセンス上問題のないものに限る。
- QGIS 依存部分は pytest-qgis などで実行する。
- 外部通信(Overpass、JOSM、MapRoulette)はテストでは模擬応答に差し替える。実サービスへの結合確認は手動の確認手順として文書化する。

| OSM のみ分類の扱い | 既定オフでよいか、参照データの網羅性をユーザーに申告させるか |

### 12.1 確認・決定結果(2026-10-04)

| 項目 | 結果 |
|---|---|
| JOSM リモートコントロール | `load_and_zoom`(`left` / `right` / `top` / `bottom` 必須、`select=way38473,node12399` 形式、`zoom_mode`、`changeset_comment` 等)で範囲読み込みと選択が可能。参照地物は `load_data`(`data` に URL エンコードした OSM XML、`new_layer=true`、`layer_name`、`upload_policy=never`、`layer_locked=true`)で別レイヤとして渡せる。接続確認は `version`(JSON で `protocolversion` を返す)。`load_data` は URL 長の制約があるため1地物ずつ送る。出典:JOSM Help/RemoteControlCommands |
| MapRoulette API | ベース `https://maproulette.org/api/v2`、認証はヘッダ `apiKey`。チャレンジ作成 `POST /challenge`(`name`、`parent`=プロジェクト ID、`instruction`、`description`、`checkinComment`、`osmIdProperty` など。本文に `localGeoJSON` を含めて一括作成も可)。タスク追加 `PUT /challenge/{id}/addFileTasks?lineByLine=true`(マルチパートの `json` フィールド。行区切り GeoJSON は各行の先頭に RS 文字 0x1E を置く RFC 7464 形式)。状態取得 `GET /challenge/{id}/tasks?limit=&page=`。タスク状態コード:0 作成、1 修正済み、2 誤検出(問題なし)、3 スキップ、4 削除、5 既に修正済み、6 難しい。OSM 地物 ID のプロパティ名は固定ではなく、チャレンジの `osmIdProperty` で指定する(本プラグインは `@id` に `node/123` 形式で入れ、`osmIdProperty="@id"` を設定する)。出典:maproulette-backend(conf/v2_route/challenge.api、ChallengeProvider.scala)、maproulette-python-client |
| 進捗同期の対応 | 1・5 → 反映済み、2 → 対応不要(未登録の候補は「参照側の誤り」、それ以外は「OSM が正しい」。M4 で再検討)、3・6 → 保留、0 → 変更しない |
| 対応 QGIS バージョン | 3.40 LTR 以上 + 4 系で確定。ローカル検証は QGIS 3.44 LTR(Qt5)、CI で 4 系も試す |
| プラグイン名 | 「OSM Diff Reviewer」で確定(公式リポジトリに同名なし。近いものに OSM Data Sync、Conflate Roads がある) |
| 初期の検証データ | M1 では架空の座標・名称で作った小さな試験データを使う。実データでの検証は後で行う |
| OSM のみ分類 | 既定はオフ。プロファイルの `reference_is_exhaustive`(参照データは網羅的)が true のときだけ出す |

リスク

- OSM コミュニティの規範:外部データの取り込みはインポートガイドラインの対象になり得る。プラグインは編集を自動化しないが、README とライセンスダイアログで注意を示す。MapRoulette で大規模なチャレンジを公開する前に地域コミュニティへ相談する旨も記す。
- 照合精度:ラインと多対多の扱いは難しい。初期版は「曖昧」に落として人が判断する設計とし、誤って「一致」に入れないことを優先する。
- Overpass の負荷:広範囲の取得は拒否・タイムアウトがあり得る。範囲の上限と、ローカルファイル利用への誘導を用意する。
- 外部 API の仕様変更:通信部分を `export/` に閉じ込め、影響範囲を限定する。

- 次に M0 と M1。照合はプロセッシングアルゴリズムとして先に作り、GUI は M2 で載せる。
- 各フェーズの完了条件は 10 の受け入れ基準とする。基準を満たすテストを先に書く。
- 閾値や探索半径の既定値は試験データで調整し、根拠を文書に残す。
- OSM へ書き込む機能は、依頼があっても本企画の範囲外として追加しない。
